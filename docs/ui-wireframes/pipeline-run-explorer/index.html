UX notes

  • 1A failed run leads with the failure: stage, record index, and exception on one line, with the partial results still reachable underneath.
  • 2Each stage card carries the same four counts in the same order everywhere in the UI: in, ok, dropped, errored.
  • 3The bar under each stage shows what proportion of records survived it, so a stage that silently eats most of the input is visible without reading numbers.
  • 4Stages that never ran are blank rather than zeroed, because zero processed and zero survived mean different things.
  • Drill-down navigation: run → stage → record, with breadcrumbs back. Low risk, matches how developers read logs top to bottom.

UX notes

  • 1Stage list, record table, and trace are on one screen, so picking a different stage or record never costs a page load or a lost scroll position.
  • 2Status filter and free-text search sit directly above the records they filter, and both are reflected in the URL so a view can be shared or refreshed.
  • 3The stage source sits under its own records, which is the pairing a developer actually needs: this code, applied to this row, produced this value.
  • 4Changed fields are highlighted against the previous stage's value, so the trace is read by scanning rather than by diffing two JSON blobs by eye.
  • Previous and next step through records sharing a status, which makes walking a run's errors quick.

UX notes

  • 1The pipeline is the navigation. Clicking a bar swaps everything below it; there is no separate stage page.
  • 2Shape first, numbers second: the funnel answers "where did my rows go" before the developer reads a single count.
  • 3Code and statistics sit side by side, which suits verifying a transformation more than debugging one bad row.
  • 4Every field shows its before and after across the selected stage, the fastest confirmation that a transformation did what was intended.
  • Weakness: single-record tracing is a second click away, so the screen serves review better than debugging.

UX notes

  • 2Keyboard-first, including a dedicated next-error key, which suits stepping through a run's failures without leaving the home row.

  • Weakness: poor for browsing. A developer who does not yet know what they are looking for gets very little scent.

UX notes

  • 1The whole run is one grid: records down, stages across. Patterns in failures are visible as shapes, for example a whole block of rows dying at the same stage.
  • 2Status is a glyph as well as a shade, so the grid stays readable without relying on colour.

  • 4The stage source for the selected column stays on screen while the developer moves between rows.
  • Weakness: the grid gets unwieldy past a handful of stages, and it implies a spreadsheet the developer might expect to edit, which this UI never allows.

Summary

Five approaches to the same data: a run, its stages, its records, and the code that transformed them.

OptionApproachBest atOverall UX
1 Drill DownHierarchical pages: run → stage → recordReading a run top to bottom the way you read a log★★★★☆
2 Split ViewStages, records, and trace side by side on one screenDebugging: changing stage or record without losing context★★★★★
3 Pipeline FunnelThe pipeline shape is the navigationReviewing whether a transformation did what was intended★★★★☆
4 Command PaletteOne keyboard-driven input addresses everythingJumping straight to a known record index★★★☆☆
5 Record MatrixA grid of records by stagesSeeing failure patterns across a whole run at once★★★☆☆

Recommendation: Option 2, Split View. The product requirement is that a developer can find the stage responsible for a wrong record in under a minute, and the split view is the only option where stage, records, source code, and trace are all reachable without navigation. Option 1's drill-down remains the fallback for narrow windows, and Option 3's funnel is worth folding into the run overview as the entry point that leads into the split view. Options 4 and 5 are strong secondary affordances rather than primary layouts: the palette is worth adding as a keyboard shortcut later, and the matrix only pays off for runs with few stages.
